Developer Guide

Customize the engine, tests, and integration points

If you want to change how meetings are run, add a new API field, or make the GUI behave differently, this is the place to start. The sections below point to the files and commands that matter most when you are modifying the project.

Where behavior lives

Area Files What you change there
Meeting logic tour_meeting/tour_meeting.py, tour_meeting/participant.py Turn selection, refinement, prompt behavior, and meeting phases.
Backend API tour_meeting/backend/api.py Meeting data, persistence, REST endpoints, and websocket payloads.
Frontend app tour_meeting/frontend/src/App.tsx, tour_meeting/frontend/src/components/Sidebar.tsx GUI flows, sidebar actions, meeting settings, and the Document link.
Docs site docs/, tour_meeting/frontend/public/docs/ Static documentation pages and the copy served through the GUI.

Run the tests that matter

Frontend and backend changes should both be exercised before you ship them. These targets are the quickest way to catch wiring mistakes or accidental regressions. 

make test-frontend
make test-backend

Use the frontend target when you change the GUI, docs link, or settings flows. Use the backend target when you change meeting storage, API payloads, or websocket events.

Common customization paths

New meeting behavior

Adjust the meeting engine when you want a different turn rule, a new refinement step, or a new phase in the meeting lifecycle.

Different API shape

Update the backend models and the frontend request helpers together so the GUI and the server keep speaking the same language.

New UI behavior

Extend the sidebar or meeting settings in the React app and then verify the corresponding backend endpoint still behaves as expected.

Docs updates

Edit the HTML pages under docs/ and mirror the change to the GUI copy so both surfaces stay in sync.

Coding agent integration

This project is designed to work with agent-like coding tools that inspect the repository, edit files, and keep the docs and GUI in sync. When you add a new workflow for that kind of assistant, keep the steps narrow and explicit so the agent can repeat them reliably.

Agent skills

Use skills when a task repeats often enough to deserve a named workflow. A good skill makes it obvious what to do, what files to touch, and which checks to run before you hand the change back.

  1. Keep the skill focused on one kind of work, such as docs updates or release prep.
  2. Name the expected files and commands so the agent does not have to infer the workflow.
  3. Update the skill when the project shape changes so the instructions stay accurate.

Before you merge a change

  1. Run the relevant frontend or backend tests.
  2. Open the GUI and verify the sidebar, meeting settings, and docs link still work.
  3. Check the docs pages in a browser and confirm the tabs, sidebar, and content still match each other.
  4. Keep unrelated local data files and scratch experiments out of the commit unless they are part of the change.
